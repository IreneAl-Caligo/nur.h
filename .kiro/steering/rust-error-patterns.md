# Rust Error Patterns in C (nur.h)

## Conceptual Mapping

| Rust                  | nur.h equivalent                        |
|-----------------------|-----------------------------------------|
| `Result<T, E>`        | `NurResult_<name>` (generated by macro) |
| `Ok(val)`             | `NUR_OK(Name, val)`                     |
| `Err(e)`              | `NUR_ERR(Name, error)`                  |
| `Option<T>`           | `NurOption_<name>`                      |
| `Some(val)`           | `NUR_SOME(Name, val)`                   |
| `None`                | `NUR_NONE(Name)`                        |
| `.unwrap()`           | `NUR_UNWRAP(r)`                         |
| `.expect("msg")`      | `NUR_EXPECT(r, "msg")`                  |
| `.unwrap_or(default)` | `NUR_UNWRAP_OR(r, default)`             |
| `?` operator          | `NUR_TRY(expr)` / `NUR_TRY_TO(...)`     |
| `is_ok()` / `is_err()`| `NUR_IS_OK(r)` / `NUR_IS_ERR(r)`        |

## Design Rules

### 1. Libraries propagate; programs unwrap.
A library function should never call `abort()`. It must propagate errors upward using `NUR_TRY` or `NUR_TRY_TO`. Only the final caller (usually `main`) decides to unwrap.

### 2. The type carries the intent.
A function returning `NurResult_i32` communicates "this can fail" as part of its signature. Never return a plain `int` from a fallible function.

### 3. Failure is normal loop progress.
Do not map a rejected result onto `error` severity in workflow steps. A `CHANGES_REQUESTED` verdict is expected output, not an exception.

### 4. Error messages are for humans; error codes are for machines.
- Use `nur_error_code_t` enum values for programmatic branching.
- Use the `message` field for developer-readable diagnostics.
- Use the `context` field for the specific value or path that caused the error.

### 5. Capture source location for free.
Always use `NUR_ERROR(code, msg)` and `NUR_ERROR_CTX(code, msg, ctx)` macros — they capture `__FILE__`, `__func__`, and `__LINE__` automatically. Never construct `nur_error_t` manually in production code.

## Error Propagation Patterns

### Pattern A: GCC/Clang (modern, idiomatic)
```c
NurResult_i32 process(const char *input) {
    int parsed = NUR_TRY(parse_int(input));   // returns on error
    int divided = NUR_TRY(safe_divide(parsed, 2));
    return NUR_OK(i32, divided);
}
```

### Pattern B: Portable C99 (all compilers)
```c
NurResult_i32 process(const char *input) {
    int parsed, divided;
    NUR_TRY_TO(i32, i32, parsed, parse_int(input));
    NUR_TRY_TO(i32, i32, divided, safe_divide(parsed, 2));
    return NUR_OK(i32, divided);
}
```

### Pattern C: Guard clauses
```c
NurResult_ptr open_safe(const char *path) {
    NUR_CHECK_AS(ptr, path != NULL, NUR_ERROR(NUR_E_NULL_POINTER, "path is null"));
    NUR_CHECK_AS(ptr, path[0] != '\0', NUR_ERROR(NUR_E_INVALID_ARGUMENT, "empty path"));
    // ... rest of logic
}
```

## Anti-patterns to Avoid

- ❌ `if (!result.ok) return NULL;` — loses the error detail
- ❌ `result.u.value` without checking `.ok` — undefined behaviour
- ❌ Nested `NUR_UNWRAP` calls — if the inner one panics, the outer is never reached
- ❌ Returning `NurResult` with a heap-allocated `message` string — the library is zero-allocation by contract; use static string literals or a caller-supplied buffer
